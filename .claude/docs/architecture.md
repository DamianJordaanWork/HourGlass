# Architecture

Clean architecture + SOLID. Dependencies point **inward**: `presentation → application → domain` and `infrastructure → domain`. The `composition` root is the only place that knows concrete adapters.

```
src/
  domain/          pure TS. entities, value objects, domain services, PORT interfaces. no I/O.
  application/     use cases + DTOs. orchestrate domain via ports. no framework, no I/O detail.
  infrastructure/  adapters implementing ports (SQLite, Harvest, ADO, calendars, OAuth, secrets, http).
  presentation/    React UI, hooks (TanStack Query + Zustand), styles/tokens.
  composition/     DI container/factory + platform detection (desktop vs web) + config bootstrap.
```

## Ports (in `domain`) → adapters (in `infrastructure`)

| Port | Adapter(s) |
|---|---|
| `IHarvestClient` | `HarvestClient` (REST v2, Bearer PAT + `Harvest-Account-Id`) |
| `IAzureDevOpsClient` | `AzureDevOpsClient` (REST v7; native composite-ID refs, CompletedWork delta) |
| `ICalendarSource` | `MicrosoftGraphCalendarClient`, `GoogleCalendarClient`, `IcsCalendarClient` |
| `IOAuthService` | `OAuthService` (PKCE + loopback via tauri-plugin-oauth) |
| `ITimeIntervalRepository`, `IMappingRuleRepository`, `IQuickTemplateRepository`, `ICalendarAccountRepository`, `IMeetingRepository`, `INoteRepository`, `ISettingsRepository` | SQLite repos |
| `ISecretStore` | OS keychain (Tauri stronghold/keyring) |
| `IHttpTransport` | Tauri HTTP plugin (desktop, no CORS) / dev-proxy (web) |
| `IClock` | system clock (injectable for tests) |

## Domain services (pure, unit-tested)

- `TemplateMatcher.resolve(context, rules)` — first enabled rule (by priority) whose conditions all match → `{harvestProjectId, harvestTaskId, noteTemplate}`.
- `IntervalAggregator` — sums intervals into per-entry hours.
- `DeadTimeCalculator` — gaps/context-switches/productivity within work-day bounds.
- `WeeklyGoalCalculator` — daily/weekly goal + expected-hours tick.

## Data model (SQLite) — summary

`time_interval` (granular unit; each Start = a new interval → its own Harvest entry by default), `mapping_rule` + `mapping_condition`, `quick_template`, `calendar_account` + `meeting`, `note` + `note_status`, `ado_connection`, `settings` (singleton). Full columns in the approved plan.

## Key flows

- **Start tracking:** create running interval (date = selected day) → resolve template → attach ADO ref → auto-stop prior timer (configurable).
- **Stop:** compute hours → POST/PATCH Harvest → write ADO native ref + `hg1` metadata → delta-sync CompletedWork.
- **Meeting log:** interval with explicit duration; prefill from event + resolved mapping.
- **Calendar sync:** OAuth per account → fetch selected day (Graph `calendarView` / Google `singleEvents`) → expand recurrences, skip all-day → upsert meetings.
- **Resilience:** SQLite is truth; every remote call best-effort with retry/reconcile; background refresh guarded by request-id so it never clobbers optimistic mutations.

## Hybrid Harvest metadata (`hg1`)

Below the user's note body (two blank lines), a fenced ` ```hg1 ` block with base64url JSON `{v,intervalId,templateId,source,ado}`, optionally scrambled/AES-encrypted (per-install keychain key). Hidden on display, decoded for reconciliation, regenerated on write. Reconciliation-only — SQLite remains source of truth.

- **ADR-022 — Reconcile divergent hours on link (refines ADR-008/009; F10, agent-tested).** `TrackingService.linkToHarvestEntry` previously attached a local interval to an existing Harvest entry (`harvestTimeEntryId`) and already set `syncedHours` to the caller-supplied `entryHours`, but never compared that to the interval's own computed duration or surfaced a mismatch — explicitly deferred at ADR-009. Policy (**Harvest wins**, unchanged in spirit, now made explicit and observable): (1) `harvestTimeEntryId` is set as before; (2) Harvest's `hours` are adopted as `syncedHours` so the *next* edit's ADO CompletedWork delta (`newHours - syncedHours`) is computed against Harvest's real total, not the interval's own pre-link duration — this is what prevents double-counting on a later edit (proven by a new test: stop a WorkItem interval at 2h, link it to a Harvest entry whose real hours are 1.5, then extend it to 3h — the ADO delta pushed is `3 - 1.5 = 1.5`, not `3 - 2 = 1`); (3) **no Harvest write happens during link** (Harvest already has the entry) and **no ADO delta is emitted** (linking isn't new logged time) — this matches `importHarvestEntry`'s existing behavior for consistency; (4) local `start`/`end` are left completely untouched — analytics timing is preserved, only `syncedHours` reflects Harvest's truth. **Return-shape decision:** `linkToHarvestEntry` now returns `LinkToHarvestResult { interval: TimeInterval; reconciled: HoursReconciliation }` instead of a bare `TimeInterval` — `HoursReconciliation { localHours, harvestHours, adopted, diverged }` (`adopted` always equals `harvestHours`, kept as a separate field for clarity at call sites and to leave room for a future "use local instead" mode without another shape change). `diverged` is `Math.abs(localHours - harvestHours) > 0.01` and only computed when the interval isn't still running (`current.end !== undefined`) — a running interval's "duration so far" isn't a meaningful thing to diverge against. Chosen over embedding the divergence as a field on `TimeInterval` itself (would pollute the persisted domain entity with a transient, link-time-only signal) or a second return value (not idiomatic TS). **Ripple kept minimal**: the only caller, `use-tracking.ts`'s `linkHarvest` mutation, passes the result through unchanged (TanStack Query doesn't care about the shape); the one UI consumer, `entry-modal.tsx`'s `LinkPicker`, updates its `onSuccess` callback to read `result.reconciled.diverged` and shows a plain `window.alert` naming both hours ("Harvest's hours were kept") before closing the picker — no new toast/notification system was introduced since none exists yet in this codebase. **Tests** (`tracking-service.test.ts`, new `describe('linkToHarvestEntry reconciliation (ADR-022)')`, 3 cases): local 2.0h vs Harvest 1.5h → `syncedHours` adopts 1.5, local `start`/`end` unchanged, `reconciled` reports `{localHours:2, harvestHours:1.5, adopted:1.5, diverged:true}`, zero Harvest create/update calls and zero ADO calls during link; matching hours within epsilon → `diverged:false`; stop-then-link-then-edit → the post-link ADO delta is computed against the adopted `syncedHours`, not the interval's pre-link hours (no double-count). The pre-existing `linkToHarvestEntry` test updated only to destructure `{ interval: linked }` from the new return shape — its assertions are otherwise unchanged. **Verified:** `npm run typecheck` — 0 errors. `npm run test` — **205 passing** (up from 202 at F9, +3, all new in the `linkToHarvestEntry reconciliation` block). `npm run build` — green, same bundle shape. **Open question (deferred, not a blocker):** whether to offer a "use local hours instead" action in the link UI, which would *push* the local computed hours to Harvest (`updateTimeEntry`) instead of adopting Harvest's — this is a genuine product/UX call (does the user ever have a reason to prefer their own clock over Harvest's already-logged entry?) and isn't implemented; the current default is deterministic Harvest-wins, always.

- **ADR-019 — Aggregate same-task-per-day roll-up (refines ADR-006 & ADR-008; F8a, agent-tested).** Behind the already-wired, OFF-by-default `Settings.aggregateSameTaskPerDay` flag, multiple same-day intervals sharing a `(harvestProjectId, harvestTaskId)` pair can now share **one** Harvest entry instead of each getting its own. Core invariant: a Harvest entry's `hours` = Σ `syncedHours` over every local interval carrying its `harvestTimeEntryId` — for a solo entry that's just the interval's own `syncedHours`, identical to today. The generalization is implemented as a **pure domain helper**, `domain/services/rollup.ts`: `resolveRollup({ interval, dayIntervals, aggregate })` returns `{ entryId?, siblingHours }` — (1) if the interval is already linked, roll into that same entry and sum every *other* same-day interval sharing that id (excludes self by id, so re-stopping a continued/edited interval never double-counts itself); (2) else, only when `aggregate` is on, look among the day's intervals for ones sharing the same project+task **and** an existing `harvestTimeEntryId`, group them by that id, and adopt the group whose earliest-started member started first (deterministic pick when a task somehow has more than one existing entry that day); (3) otherwise (aggregate off, or nothing to join) → `{ entryId: undefined, siblingHours: 0 }`, i.e. no roll-up — a fresh entry will be created holding just this interval's own hours. `sumSyncedHours` (also exported, `undefined → 0`) is the shared summation primitive, reused by both the resolver and `TrackingService.deleteInterval`'s patch-down path. **`TrackingService.pushToHarvest`** now destructures `aggregateSameTaskPerDay` off `settings.get()`, fetches the day's intervals (`listByDate(interval.date)` — called *before* the current interval's own upsert, so it never includes the not-yet-persisted current interval; `resolveRollup` excludes self by id regardless, as a second guard), calls `resolveRollup`, and computes `absoluteHours = round2(siblingHours + hours)`: if `entryId` resolved, `harvest.updateTimeEntry(entryId, { hours: absoluteHours, ... })` (patches the shared entry to the new group total); else `createTimeEntry({ hours: absoluteHours, ... })` (== `hours` when solo, so OFF/solo is byte-for-byte the pre-existing behavior). The **ADO CompletedWork delta block is untouched** — `delta = round2(hours - (interval.syncedHours ?? 0))`, still computed per-interval, never against the group sum — and the returned interval still carries `syncedHours: hours` (this interval's own contribution only, not the group total), so per-member ADO bookkeeping and the timesheet's per-interval hours stay exactly as before; only the value pushed to the *shared Harvest entry* changes. **`TrackingService.deleteInterval`** changes from unconditional `deleteTimeEntry` to **patch-down-else-delete**: fetch the interval (`get(id)`) *before* deleting it locally, then delete; if it had a `harvestTimeEntryId` and a Harvest client is configured, compute `remaining` = the day's intervals still sharing that id (naturally excludes the just-deleted one, since local delete already happened) — if `remaining.length === 0`, `deleteTimeEntry` (solo/OFF case: deletes exactly as before); otherwise `updateTimeEntry(id, { hours: round2(sumSyncedHours(remaining)) })` (patches the shared entry down to the survivors' total). New, **applies in both modes** (ADR-008 refinement, not gated by the flag): after the Harvest branch, if `ado` is configured and the deleted interval had a `workItemRef` and a non-zero `syncedHours`, best-effort `ado.syncCompletedWork(connectionId, workItemId, round2(-syncedHours))` — decrements ADO's CompletedWork by exactly what that interval had contributed, so deleting a synced interval no longer leaves ADO permanently over-counted. Both new remote calls are wrapped in the existing try/catch-warn pattern — never throws, never blocks the local delete. **Forward-only**: no retro-consolidation pass merges pre-existing separate entries when the flag is turned on after the fact; roll-up only ever joins entries going forward from intervals still resolvable via `listByDate`. **Tests**: `domain/services/rollup.test.ts` (8 cases, pure) covers solo/OFF-unlinked (no rollup), OFF-but-self-linked (sums other same-entry sharers, excludes a different entry), ON-first-of-task (nothing to join), ON-one-linked-sibling (joins it), ON-re-stop-excludes-self, ON-multiple-candidate-entries (earliest-start wins), ON-different-task-or-date (no rollup), and `sumSyncedHours` undefined-safety. `application/tracking-service.test.ts` gained a new `describe('aggregateSameTaskPerDay roll-up')` block (6 cases) proving: ON two-stops-same-task/day → one create + one patch to the cumulative sum, correct per-interval ADO deltas, a third stop keeps patching the cumulative total; OFF (default settings, unchanged) → two creates, explicit `harvest.updated` length-0 assertion (no cross-update); ON `continueInterval` on a group member then stopping → patches the sum, no new create; ON `updateInterval` on a member → patches the recomputed sum, ADO gets only that member's own delta; ON delete-one-of-two → patches the entry down to the survivor (not deleted) with the correct ADO decrement, then deleting the survivor actually deletes the Harvest entry (`harvest.deleted` asserted) with its own ADO decrement; ON with no Harvest client (demo mode) → stays local, never throws. **All 10 pre-existing `TrackingService` tests pass completely unchanged**, proving OFF is a provable no-op (167 → 181 total tests: +8 `rollup.test.ts` + 6 new `tracking-service.test.ts` cases = +14 net). **Open questions / explicitly deferred**: rolled-entry `notes` are last-writer-wins (whichever interval pushes last overwrites the shared entry's notes — no per-member note concatenation); cross-task edits (changing a member's project/task mid-group) don't rebalance the old group's total, they just start fresh under the new task; external Harvest-only entries (never adopted locally) are excluded from every rollup computation, same as they always were from local bookkeeping; retro-consolidation (merging already-separate entries when the flag flips on) is not implemented — only forward pushes join.

ON CONFLICT(calendar_account_id, external_uid, date) DO UPDATE` inside one transaction (dedupe-by-natural-key, matching the ICS/Graph re-sync semantics); `QuickTemplate`/`Note` order by `sort_order`; `AdoConnection` orders by `label`; `Settings.get` returns `{...DEFAULT_SETTINGS, ...rowToSettings(row)}` when the singleton row exists else `DEFAULT_SETTINGS` untouched, and `save` uses `INSERT OR REPLACE` keyed on the `CHECK (id=1)` PK so there is never more than one settings row. `app-repositories.ts` introduces `AppRepositories` (the 8-port shape both backends now satisfy) and `RepositoriesFacade`, which proxies a `Promise<AppRepositories>` method-by-method (`async m(...a) { return (await backend).repo.m(...a) }`) — this is what lets `createContainer()` hand out a **synchronously constructible** repos object immediately while the real backend (WASM init + migrations + one-time import) resolves in the background; `local-repositories.ts`'s `LocalRepositories` now `extends AppRepositories` (structurally already conformed; the fallback backend is otherwise unchanged). `create-web-repositories.ts`'s `createWebRepositories()` is the composition entry point: try WASM SQLite (`createWebSqlDatabase()` → `createSqlRepositories(db)` → one-time `migrateLocalStorageIntoSql`) and return those repos; on **any** failure (sql.js/WASM unavailable, IndexedDB blocked, etc.) log an error and fall back to `createLocalRepositories()` — wrapped in `RepositoriesFacade` either way, so callers never know which backend they got. `migrate-localstorage.ts`'s `migrateLocalStorageIntoSql(repos, storage?)` is a one-time import guarded by a `hourglass.migratedToSqlite` localStorage flag: if any legacy `hourglass.*` collection key exists, it reads each via the existing `LocalCollection`/`LocalValue` machinery and bulk-upserts through the SQL repos, then sets the flag; it **never deletes** localStorage data, which remains the fallback store if WASM becomes unavailable on a later run. `container.ts` now awaits `createWebRepositories()`'s `ready` **before** `connections.reconfigure()` inside the existing `ready` promise, preserving the seed-demo/clear-broken-seed sequencing exactly; a comment marks the `isTauri()` seam for F4, which will reuse `createSqlRepositories()` unchanged against a Tauri-sql-backed `ISqlDatabase` instead of `WasmSqlDatabase` — everything above `ISqlDatabase` (mappers, repos, facade, migration import) carries forward untouched. Test-side, `src/test/wasm-sql-database.ts`'s `createInMemoryWasmDatabase()` gives Node tests a real, migrated, in-memory `WasmSqlDatabase` (no `load`/`save`) without ever touching the `?url` asset import; `wasm-sql-database.test.ts` and `sql-repositories.test.ts` exercise it directly (all 10 tables + `schema_migrations` created, `PRAGMA foreign_keys` reads `1`, execute/query round-trip + `rowsAffected`, boolean coercion, transaction commit/rollback-to-`SqlError`, positional params, malformed-SQL → `SqlError`; per-repo round-trip incl. null/JSON fidelity, running-interval semantics, `MappingRule` priority + seq ordering and condition-set replacement, FK cascades (`rule→condition`, `calendar_account→meeting`), `Settings` singleton-row merge, `Meeting.upsertMany` natural-key dedupe, and every specified `ORDER BY`). - **ADR-013 — `ISqlDatabase` is an infrastructure-boundary port; SQLite schema v1 reconciled against real entities.** New `infrastructure/persistence/sql/sql-database.ts` defines `ISqlExecutor` (`execute(sql, params?)`, `query<T>(sql, params?)`) and `ISqlDatabase extends ISqlExecutor` (`transaction(work)`), with `SqlParam = string | number | boolean | null`. Unlike domain ports (`ITimeIntervalRepository` etc.), this port deliberately lives in **infrastructure**, not `domain` — SQL is an infra concern per the layer rules; the domain-facing seam stays the existing repository ports, which a future SQL-backed repo will implement by composing `ISqlDatabase` underneath (F3/F4). This is a deliberate contrast with `IHttpTransport` (also infra) — same rationale, different I/O shape: async, positional `?` params, callback-style `transaction`. No concrete driver ships in this slice (no Tauri SQL plugin, no sql.js/WASM dependency) — `ISqlDatabase` exists purely as a stable, fake-able seam. `schema.ts` exports `SCHEMA_V1: readonly string[]`, 10 `CREATE TABLE IF NOT EXISTS` statements (+ 3 indexes: `idx_time_interval_date`, a partial `idx_time_interval_running` on `end_time IS NULL`, `idx_meeting_date`) reconciled against the **real** domain entities rather than the original master-plan sketch. Corrections made: `time_interval` gains `synced_hours` (from `TimeInterval.syncedHours`, ADR-008); `meeting` gains `calendar_name` (from `Meeting.calendarName`) and a `UNIQUE(calendar_account_id, external_uid, date)` constraint; `ado_connection` uses `org_url` (not `base_url`) + `iteration_path`, and drops `pat_ref`/`sync_completed_work`/`harvest_guid_learned` (none exist on `AdoConnection` — the PAT lives in `ISecretStore`, not the row); `calendar_account` drops `token_ref` (OAuth tokens live in `ISecretStore` via `calendarTokenKey`/`calendarRefreshKey`, not the row); `note` drops `type` and `status_id` (no such fields on `Note`) and gains `created_at`; `note_status` is present but **unused** by any FK (forward-compat placeholder only, per plan); `settings` carries the full `Settings` field set 1:1 (`work_day_start/end`, `break_minutes`, `min_dead_time_minutes`, `weekly_goal_hours`, `refresh_interval_minutes`, `theme`, `harvest_account_id`, `microsoft_client_id`, `default_project_id/task_id`, `auto_stop_on_switch`, `aggregate_same_task_per_day`, `embed_metadata`, `hg1_scheme`), keyed by `id INTEGER PRIMARY KEY CHECK (id = 1)` (singleton row). Migration strategy: `migrations.ts` defines `Migration { version, name, statements }` and an append-only `MIGRATIONS` array (currently just `{version: 1, name: 'schema_v1', statements: SCHEMA_V1}`); `migration-runner.ts`'s `runMigrations(db, migrations?, nowIso?)` bootstraps a `schema_migrations(version, name, applied_at)` table, reads already-applied versions, sorts the input ascending (throws `MigrationError` on duplicate/non-increasing versions), and applies each not-yet-applied migration's statements **plus** its `schema_migrations` INSERT inside **one** `db.transaction` call — so a mid-migration failure rolls back the whole migration (no partial DDL, no phantom version record) and rethrows. Forward-only, idempotent (repeat calls apply nothing once caught up), data-driven (new versions just append to `MIGRATIONS`). `nowIso` is injected (defaults to `() => new Date().toISOString()`) for deterministic tests — `new Date()` is acceptable here specifically because this module is infrastructure, not domain (domain still must inject `IClock`). Test split: `migration-runner.test.ts` exercises runner logic only (fresh apply, idempotency, forward append incl. a synthetic v2, out-of-order input sorted ascending, duplicate/non-increasing → `MigrationError`, transaction-rollback via injected failure, injected `nowIso` surfacing in `applied_at`) against `src/test/fake-sql-database.ts` (a recording fake that only understands `schema_migrations` semantics — tracks applied versions in a `Set`, answers the runner's `SELECT`/`INSERT` against it, and treats every other statement as opaque/unparsed, plus a `failOn` substring hook for rollback tests); `schema.test.ts` asserts `SCHEMA_V1`'s shape as pure strings (table count/names, `IF NOT EXISTS` on every statement, the specific corrections above) with **no execution** — actual DDL correctness (does SQLite accept these strings, do FKs/indexes really work) is deferred to F3 when a real driver exists to run them against.
- **ADR-012 — Pluggable hg1 encoding behind a sync domain `Hg1Codec` port (refines ADR-009).** `Hg1Codec` (`domain/harvest/hg1-codec.ts`: `{ scheme, encode(json): string, decode(body): string|null }`, `Hg1CodecUnavailableError`) makes the hg1 fenced-block body self-describing: a `<letter><digit>:` prefix (e.g. `s1:`) names the scheme; an unprefixed body is `plain` — byte-for-byte identical to the pre-pluggable format (base64url never contains `:`, so detection is unambiguous, no migration needed). `plainHg1Codec` (`plain-hg1-codec.ts`, hosts the `toBase64Url`/`fromBase64Url` helpers moved from `hg1-metadata.ts`) and `scrambleHg1Codec` (`scramble-hg1-codec.ts`, keyless reversible UTF-8 XOR + base64url, prefixed `s1:`) are both pure/sync and live in `domain/`. `hg1-codec-registry.ts` exposes `codecFor(scheme)` (explicit choice, e.g. from Settings) and `codecForBody(body)` (auto-detect for decode). `Hg1.encode`/`embed` (`hg1-metadata.ts`) take an optional `codec` param defaulting to `plainHg1Codec`; `Hg1.extract` always resolves the codec per-body via `codecForBody`, so tags written under different schemes over time all remain decodable through the same call. `Settings.hg1Scheme: Hg1Scheme` (default `'plain'`) is only consulted when `embedMetadata` is on; `TrackingService.pushToHarvest` reads it alongside `embedMetadata` and resolves `codecFor(scheme)`. `aes` (`a1:`) is reserved in the type but deliberately **not implemented** — `codecFor('aes')` throws `Hg1CodecUnavailableError`; real encryption needs a key and therefore async I/O against `ISecretStore`, which doesn't fit the domain layer's pure/sync constraint (ADR-002's "no I/O in domain") — it will need an infra-level adapter/wrapper when built. Open questions (deferred): AES key provenance (per-install `ISecretStore` key vs user passphrase), the AES portability tradeoff (an encrypted tag isn't decodable on a fresh install, which cuts against hg1's own recovery purpose), and whether to expose `scramble` in the Settings UI yet (currently only reachable by changing the default/DB value).

- **ADR-009 — Harvest is the source of truth (refines ADR-002).** Per product direction, a persisted entry is meaningful only when linked to a Harvest entry (`harvestTimeEntryId`); local SQLite is the working cache/link + analytics store, not the authority. Consequences implemented: (a) **hg1 stores only non-native data** — `{ v, source, templateId? }`; project/task/notes/hours/date and the ADO link (native `external_reference`) are dropped. Embedding is **opt-in via `Settings.embedMetadata` (default false)** and, even when on, only written when non-default; turning it off strips the tag on the next sync (keeps Harvest notes clean by default). (b) **Never push `hours ≤ 0`** — Harvest treats a timeless entry as a *running* timer, which would collide with our local timing (dual timer); we time locally and always push explicit positive hours on stop. (c) **Harvest entries are first-class**: `importHarvestEntry` adopts an external entry into a local interval; `linkToHarvestEntry` attaches a local interval to an existing Harvest entry; external (Harvest-only) rows support Start (new timer)/Edit(adopt+update)/Delete(`deleteTimeEntry`). (d) **Delete moved into the edit modal** behind a two-step confirm (card delete was too easy to hit). Deferred: blocking starts that can't map to Harvest. *(Update, F10: reconciling divergent hours on link is now implemented — see ADR-022.)*

- **ADR-007 — Runtime connection wiring via a `ConnectionManager` + lazy client providers.** Real Harvest/ADO adapters are built from persisted config + secrets by `infrastructure/connections/connection-manager.ts`, which holds the live clients and rebuilds them on `reconfigure()` (called after any Settings save).
