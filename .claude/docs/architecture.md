# Architecture

Clean architecture + SOLID. Dependencies point **inward**: `presentation → application → domain` and `infrastructure → domain`. The `composition` root is the only place that knows concrete adapters.

```
src/
  domain/          pure TS. entities, value objects, domain services, PORT interfaces. no I/O.
  application/     use cases + DTOs. orchestrate domain via ports. no framework, no I/O detail.
  infrastructure/  adapters implementing ports (SQLite, Harvest, ADO, calendars, OAuth, secrets, http).
  presentation/    React UI, hooks (TanStack Query + Zustand), styles/tokens.
  composition/     DI container/factory + platform detection (desktop vs web) + config bootstrap.
```

## Ports (in `domain`) → adapters (in `infrastructure`)

| Port | Adapter(s) |
|---|---|
| `IHarvestClient` | `HarvestClient` (REST v2, Bearer PAT + `Harvest-Account-Id`) |
| `IAzureDevOpsClient` | `AzureDevOpsClient` (REST v7; native composite-ID refs, CompletedWork delta) |
| `ICalendarSource` | `MicrosoftGraphCalendarClient`, `GoogleCalendarClient`, `IcsCalendarClient` |
| `IOAuthService` | `OAuthService` (PKCE + loopback via tauri-plugin-oauth) |
| `ITimeIntervalRepository`, `IMappingRuleRepository`, `IQuickTemplateRepository`, `ICalendarAccountRepository`, `IMeetingRepository`, `INoteRepository`, `ISettingsRepository` | SQLite repos |
| `ISecretStore` | OS keychain (Tauri stronghold/keyring) |
| `IHttpTransport` | Tauri HTTP plugin (desktop, no CORS) / dev-proxy (web) |
| `IClock` | system clock (injectable for tests) |

## Domain services (pure, unit-tested)

- `TemplateMatcher.resolve(context, rules)` — first enabled rule (by priority) whose conditions all match → `{harvestProjectId, harvestTaskId, noteTemplate}`.
- `IntervalAggregator` — sums intervals into per-entry hours.
- `DeadTimeCalculator` — gaps/context-switches/productivity within work-day bounds.
- `WeeklyGoalCalculator` — daily/weekly goal + expected-hours tick.

## Data model (SQLite) — summary

`time_interval` (granular unit; each Start = a new interval → its own Harvest entry by default), `mapping_rule` + `mapping_condition`, `quick_template`, `calendar_account` + `meeting`, `note` + `note_status`, `ado_connection`, `settings` (singleton). Full columns in the approved plan.

## Key flows

- **Start tracking:** create running interval (date = selected day) → resolve template → attach ADO ref → auto-stop prior timer (configurable).
- **Stop:** compute hours → POST/PATCH Harvest → write ADO native ref + `hg1` metadata → delta-sync CompletedWork.
- **Meeting log:** interval with explicit duration; prefill from event + resolved mapping.
- **Calendar sync:** OAuth per account → fetch selected day (Graph `calendarView` / Google `singleEvents`) → expand recurrences, skip all-day → upsert meetings.
- **Resilience:** SQLite is truth; every remote call best-effort with retry/reconcile; background refresh guarded by request-id so it never clobbers optimistic mutations.

## Hybrid Harvest metadata (`hg1`)

Below the user's note body (two blank lines), a fenced ` ```hg1 ` block with base64url JSON `{v,intervalId,templateId,source,ado}`, optionally scrambled/AES-encrypted (per-install keychain key). Hidden on display, decoded for reconciliation, regenerated on write. Reconciliation-only — SQLite remains source of truth.

## ADR log

- **ADR-013 — `ISqlDatabase` is an infrastructure-boundary port; SQLite schema v1 reconciled against real entities.** New `infrastructure/persistence/sql/sql-database.ts` defines `ISqlExecutor` (`execute(sql, params?)`, `query<T>(sql, params?)`) and `ISqlDatabase extends ISqlExecutor` (`transaction(work)`), with `SqlParam = string | number | boolean | null`. Unlike domain ports (`ITimeIntervalRepository` etc.), this port deliberately lives in **infrastructure**, not `domain` — SQL is an infra concern per the layer rules; the domain-facing seam stays the existing repository ports, which a future SQL-backed repo will implement by composing `ISqlDatabase` underneath (F3/F4). This is a deliberate contrast with `IHttpTransport` (also infra) — same rationale, different I/O shape: async, positional `?` params, callback-style `transaction`. No concrete driver ships in this slice (no Tauri SQL plugin, no sql.js/WASM dependency) — `ISqlDatabase` exists purely as a stable, fake-able seam. `schema.ts` exports `SCHEMA_V1: readonly string[]`, 10 `CREATE TABLE IF NOT EXISTS` statements (+ 3 indexes: `idx_time_interval_date`, a partial `idx_time_interval_running` on `end_time IS NULL`, `idx_meeting_date`) reconciled against the **real** domain entities rather than the original master-plan sketch. Corrections made: `time_interval` gains `synced_hours` (from `TimeInterval.syncedHours`, ADR-008); `meeting` gains `calendar_name` (from `Meeting.calendarName`) and a `UNIQUE(calendar_account_id, external_uid, date)` constraint; `ado_connection` uses `org_url` (not `base_url`) + `iteration_path`, and drops `pat_ref`/`sync_completed_work`/`harvest_guid_learned` (none exist on `AdoConnection` — the PAT lives in `ISecretStore`, not the row); `calendar_account` drops `token_ref` (OAuth tokens live in `ISecretStore` via `calendarTokenKey`/`calendarRefreshKey`, not the row); `note` drops `type` and `status_id` (no such fields on `Note`) and gains `created_at`; `note_status` is present but **unused** by any FK (forward-compat placeholder only, per plan); `settings` carries the full `Settings` field set 1:1 (`work_day_start/end`, `break_minutes`, `min_dead_time_minutes`, `weekly_goal_hours`, `refresh_interval_minutes`, `theme`, `harvest_account_id`, `microsoft_client_id`, `default_project_id/task_id`, `auto_stop_on_switch`, `aggregate_same_task_per_day`, `embed_metadata`, `hg1_scheme`), keyed by `id INTEGER PRIMARY KEY CHECK (id = 1)` (singleton row). Migration strategy: `migrations.ts` defines `Migration { version, name, statements }` and an append-only `MIGRATIONS` array (currently just `{version: 1, name: 'schema_v1', statements: SCHEMA_V1}`); `migration-runner.ts`'s `runMigrations(db, migrations?, nowIso?)` bootstraps a `schema_migrations(version, name, applied_at)` table, reads already-applied versions, sorts the input ascending (throws `MigrationError` on duplicate/non-increasing versions), and applies each not-yet-applied migration's statements **plus** its `schema_migrations` INSERT inside **one** `db.transaction` call — so a mid-migration failure rolls back the whole migration (no partial DDL, no phantom version record) and rethrows. Forward-only, idempotent (repeat calls apply nothing once caught up), data-driven (new versions just append to `MIGRATIONS`). `nowIso` is injected (defaults to `() => new Date().toISOString()`) for deterministic tests — `new Date()` is acceptable here specifically because this module is infrastructure, not domain (domain still must inject `IClock`). Test split: `migration-runner.test.ts` exercises runner logic only (fresh apply, idempotency, forward append incl. a synthetic v2, out-of-order input sorted ascending, duplicate/non-increasing → `MigrationError`, transaction-rollback via injected failure, injected `nowIso` surfacing in `applied_at`) against `src/test/fake-sql-database.ts` (a recording fake that only understands `schema_migrations` semantics — tracks applied versions in a `Set`, answers the runner's `SELECT`/`INSERT` against it, and treats every other statement as opaque/unparsed, plus a `failOn` substring hook for rollback tests); `schema.test.ts` asserts `SCHEMA_V1`'s shape as pure strings (table count/names, `IF NOT EXISTS` on every statement, the specific corrections above) with **no execution** — actual DDL correctness (does SQLite accept these strings, do FKs/indexes really work) is deferred to F3 when a real driver exists to run them against.
- **ADR-012 — Pluggable hg1 encoding behind a sync domain `Hg1Codec` port (refines ADR-009).** `Hg1Codec` (`domain/harvest/hg1-codec.ts`: `{ scheme, encode(json): string, decode(body): string|null }`, `Hg1CodecUnavailableError`) makes the hg1 fenced-block body self-describing: a `<letter><digit>:` prefix (e.g. `s1:`) names the scheme; an unprefixed body is `plain` — byte-for-byte identical to the pre-pluggable format (base64url never contains `:`, so detection is unambiguous, no migration needed). `plainHg1Codec` (`plain-hg1-codec.ts`, hosts the `toBase64Url`/`fromBase64Url` helpers moved from `hg1-metadata.ts`) and `scrambleHg1Codec` (`scramble-hg1-codec.ts`, keyless reversible UTF-8 XOR + base64url, prefixed `s1:`) are both pure/sync and live in `domain/`. `hg1-codec-registry.ts` exposes `codecFor(scheme)` (explicit choice, e.g. from Settings) and `codecForBody(body)` (auto-detect for decode). `Hg1.encode`/`embed` (`hg1-metadata.ts`) take an optional `codec` param defaulting to `plainHg1Codec`; `Hg1.extract` always resolves the codec per-body via `codecForBody`, so tags written under different schemes over time all remain decodable through the same call. `Settings.hg1Scheme: Hg1Scheme` (default `'plain'`) is only consulted when `embedMetadata` is on; `TrackingService.pushToHarvest` reads it alongside `embedMetadata` and resolves `codecFor(scheme)`. `aes` (`a1:`) is reserved in the type but deliberately **not implemented** — `codecFor('aes')` throws `Hg1CodecUnavailableError`; real encryption needs a key and therefore async I/O against `ISecretStore`, which doesn't fit the domain layer's pure/sync constraint (ADR-002's "no I/O in domain") — it will need an infra-level adapter/wrapper when built. Open questions (deferred): AES key provenance (per-install `ISecretStore` key vs user passphrase), the AES portability tradeoff (an encrypted tag isn't decodable on a fresh install, which cuts against hg1's own recovery purpose), and whether to expose `scramble` in the Settings UI yet (currently only reachable by changing the default/DB value).
- **ADR-011 — Calendar providers built: ICS + Microsoft Graph, web-popup OAuth, no Tauri dependency.** `IcsCalendarSource` (`infrastructure/calendar/ics-calendar-source.ts`, via `ical.js`) and `MicrosoftGraphCalendarSource` (`.../microsoft-graph-calendar-source.ts`, resolver-callback shape like `AzureDevOpsClient`) both implement `ICalendarSource`. OAuth is `WebRedirectOAuthService` (`infrastructure/oauth/`): PKCE (`pkce.ts`, Web Crypto `crypto.subtle`) + a popup to the provider's authorize page + `oauth-callback.tsx` (rendered by `App.tsx` when `location.search` has `oauth=callback`) `postMessage`s the code back to the opener, which exchanges it directly against the token endpoint (no proxy needed — SPA-type Azure AD app registrations send permissive CORS on `/token`). This ships forward unchanged for desktop; only the `IOAuthService` implementation swaps to a Tauri loopback listener later. `ConnectionManager` gained `calendars()` (account id → shared per-provider `ICalendarSource` instance, rebuilt in `reconfigure()`), `saveCalendarAccount`/`deleteCalendarAccount`/`connectMicrosoftAccount`/`probeCalendarAccount`. `container.listMeetings(date)` now syncs every enabled account's `fetchDay` best-effort (a provider hiccup logs a warning, never blanks the day) before reading the merged local cache; demo fallback only when zero calendar accounts exist AND `isConfigured()` is false. `Settings.microsoftClientId` stores the user's own Azure AD app registration Client ID (public, not a secret — Hourglass has no bundled shared client, see plan). New `CalendarsSection` in `settings.tsx` mirrors `AdoSection`'s list+docked-form pattern. All-day meetings (`Meeting.isAllDay`) show in the source rail without a one-click Start affordance. Deferred: proactive token refresh (Graph tokens are stored but not auto-refreshed on expiry — a later pass once real usage shows it's needed), Google Calendar (same OAuth2/PKCE shape, cheap to add behind the same ports), background polling (`Settings.refreshIntervalMinutes` still unused — sync stays on-demand per selected day).
- **ADR-001 — Stack: React+TS+Tauri.** Chosen over Flutter and C#/.NET after mobile was dropped from scope; Tauri gives standalone desktop + a web build from one React UI. See plan.
- **ADR-002 — Storage: SQLite hybrid.** Local-first SQLite (serverless, portable, keeps interval analytics) + embedded Harvest metadata; rejected fully-SQL-less (fragile) and server DB (blocks standalone).
- **ADR-003 — Desktop-first for API calls.** Harvest/ADO/calendars reject browser CORS; Tauri HTTP plugin proxies via Rust. Web target adds a thin proxy in Phase 3.
- **ADR-004 — Tailwind v4 + CSS-variable tokens.** Tokens in `src/presentation/styles/tokens.css` are the single source of truth, mapped into Tailwind via `@theme inline`. Theme via `data-theme` on `<html>` + `prefers-color-scheme`.
- **ADR-005 — Vitest 3 (not 2).** Vitest 2 pinned its own Vite 5 under our Vite 6, causing plugin type clashes; Vitest 3 dedupes to a single Vite 6.
- **ADR-006 — Each Start = separate Harvest entry.** Per user requirement (no roll-up). Optional aggregate toggle deferred to Phase 2.
- **ADR-010 — Enforce the Harvest-link invariant, end to end.** `TrackingService.startTracking`/`logManualTime`/`updateInterval` now throw `UnmappedEntryError` (`domain/errors.ts`) when the resolved project+task is missing/partial — refusing to persist an entry Harvest can't represent. At the UI boundary, `EntryModal` no longer auto-defaults a new entry's project to the first option (a silent guess defeats the point); the Save/Start/Add button is disabled with a hint until a project **and** task are chosen. Start/Log actions whose mapping rule doesn't resolve (`WorkItemCard`, `MeetingCard`, quick templates) no longer call `startTracking` directly — they route through a global `useEntryModalStore` (`presentation/state/entry-modal.ts`) that opens the same modal prefilled with the original context (notes, `workItemRef`, `templateId`, `source`, and a meeting's computed duration for "Log"), so the user picks a mapping without losing why the entry was started. Already-mapped items keep the zero-friction one-click Start. Continuing/importing/linking don't need the guard (they never introduce a fresh unmapped entry).
- **ADR-009 — Harvest is the source of truth (refines ADR-002).** Per product direction, a persisted entry is meaningful only when linked to a Harvest entry (`harvestTimeEntryId`); local SQLite is the working cache/link + analytics store, not the authority. Consequences implemented: (a) **hg1 stores only non-native data** — `{ v, source, templateId? }`; project/task/notes/hours/date and the ADO link (native `external_reference`) are dropped. Embedding is **opt-in via `Settings.embedMetadata` (default false)** and, even when on, only written when non-default; turning it off strips the tag on the next sync (keeps Harvest notes clean by default). (b) **Never push `hours ≤ 0`** — Harvest treats a timeless entry as a *running* timer, which would collide with our local timing (dual timer); we time locally and always push explicit positive hours on stop. (c) **Harvest entries are first-class**: `importHarvestEntry` adopts an external entry into a local interval; `linkToHarvestEntry` attaches a local interval to an existing Harvest entry; external (Harvest-only) rows support Start (new timer)/Edit(adopt+update)/Delete(`deleteTimeEntry`). (d) **Delete moved into the edit modal** behind a two-step confirm (card delete was too easy to hit). Deferred: blocking starts that can't map to Harvest; reconciling divergent hours on link.
- **ADR-008 — Edit/restart/manual entries + Harvest-entry reconciliation.** `TimeInterval` gained `syncedHours` (hours last pushed) so edits push **absolute** hours to Harvest but only the **delta** (`newHours − syncedHours`) to ADO CompletedWork — no double-counting on re-sync. `TrackingService.updateInterval` (marks `isManual`, re-derives hours from start/end, re-pushes) and `continueInterval` (reopens the SAME stopped interval — shifts `start` back by the already-logged time so the clock resumes from the accrued total and the next stop updates the same Harvest entry; **not** a clone — the user wants to continue, not restart) added. The timesheet reconciles by `harvestTimeEntryId`: Harvest entries matching a local interval are hidden (local wins, editable); unmatched Harvest entries render **read-only** ("Harvest" badge) and count toward day/week totals. Editing/adopting those external entries is deferred. Manual/edit uses one modal (`entry-modal.tsx`) with an optional time editor — any of start+end, start+duration, end+duration, or duration-only (fields kept in sync; times are local HH:MM ↔ ISO). New + all-blank → live `startTracking`; otherwise `logManualTime`/`updateInterval` with the resolved start/end. Web dev pulls entries through the Vite proxy (ADR-003/007).
- **ADR-007 — Runtime connection wiring via a `ConnectionManager` + lazy client providers.** Real Harvest/ADO adapters are built from persisted config + secrets by `infrastructure/connections/connection-manager.ts`, which holds the live clients and rebuilds them on `reconfigure()` (called after any Settings save). It lives in infrastructure because it constructs concrete adapters; the composition root wires it and the container falls back to seeded demo data whenever `configured()` is false. `TrackingService.harvest/ado` became **provider functions** (`() => IHarvestClient | undefined`) so the manager can swap the underlying client without rebuilding the service and so demo mode skips sync silently (no spurious warnings). Rejected: rebuilding the whole container/tracking-service on config change (the container is a stable singleton read live by hooks) and always-present delegating clients (would emit false sync warnings in demo mode). Secrets go through `ISecretStore`; the web/dev adapter (`LocalSecretStore`) is localStorage-backed (**not** hardware-backed) and is swapped for the OS keychain (Tauri stronghold) on desktop behind the same port. `IHttpTransport` currently resolves to `FetchHttpTransport` for both platforms (`createHttpTransport()`); the Tauri native branch (no CORS) slots in there later. ADR-003's CORS caveat stands: live Harvest/ADO calls only work in the desktop shell (or via a web proxy) — the plain web build will fail direct calls.
