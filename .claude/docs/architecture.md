# Architecture

Clean architecture + SOLID. Dependencies point **inward**: `presentation → application → domain` and `infrastructure → domain`. The `composition` root is the only place that knows concrete adapters.

```
src/
  domain/          pure TS. entities, value objects, domain services, PORT interfaces. no I/O.
  application/     use cases + DTOs. orchestrate domain via ports. no framework, no I/O detail.
  infrastructure/  adapters implementing ports (SQLite, Harvest, ADO, calendars, OAuth, secrets, http).
  presentation/    React UI, hooks (TanStack Query + Zustand), styles/tokens.
  composition/     DI container/factory + platform detection (desktop vs web) + config bootstrap.
```

## Ports (in `domain`) → adapters (in `infrastructure`)

| Port | Adapter(s) |
|---|---|
| `IHarvestClient` | `HarvestClient` (REST v2, Bearer PAT + `Harvest-Account-Id`) |
| `IAzureDevOpsClient` | `AzureDevOpsClient` (REST v7; native composite-ID refs, CompletedWork delta) |
| `ICalendarSource` | `MicrosoftGraphCalendarClient`, `GoogleCalendarClient`, `IcsCalendarClient` |
| `IOAuthService` | `OAuthService` (PKCE + loopback via tauri-plugin-oauth) |
| `ITimeIntervalRepository`, `IMappingRuleRepository`, `IQuickTemplateRepository`, `ICalendarAccountRepository`, `IMeetingRepository`, `INoteRepository`, `ISettingsRepository` | SQLite repos |
| `ISecretStore` | OS keychain (Tauri stronghold/keyring) |
| `IHttpTransport` | Tauri HTTP plugin (desktop, no CORS) / dev-proxy (web) |
| `IClock` | system clock (injectable for tests) |

## Domain services (pure, unit-tested)

- `TemplateMatcher.resolve(context, rules)` — first enabled rule (by priority) whose conditions all match → `{harvestProjectId, harvestTaskId, noteTemplate}`.
- `IntervalAggregator` — sums intervals into per-entry hours.
- `DeadTimeCalculator` — gaps/context-switches/productivity within work-day bounds.
- `WeeklyGoalCalculator` — daily/weekly goal + expected-hours tick.

## Data model (SQLite) — summary

`time_interval` (granular unit; each Start = a new interval → its own Harvest entry by default), `mapping_rule` + `mapping_condition`, `quick_template`, `calendar_account` + `meeting`, `note` + `note_status`, `ado_connection`, `settings` (singleton). Full columns in the approved plan.

## Key flows

- **Start tracking:** create running interval (date = selected day) → resolve template → attach ADO ref → auto-stop prior timer (configurable).
- **Stop:** compute hours → POST/PATCH Harvest → write ADO native ref + `hg1` metadata → delta-sync CompletedWork.
- **Meeting log:** interval with explicit duration; prefill from event + resolved mapping.
- **Calendar sync:** OAuth per account → fetch selected day (Graph `calendarView` / Google `singleEvents`) → expand recurrences, skip all-day → upsert meetings.
- **Resilience:** SQLite is truth; every remote call best-effort with retry/reconcile; background refresh guarded by request-id so it never clobbers optimistic mutations.

## Hybrid Harvest metadata (`hg1`)

Below the user's note body (two blank lines), a fenced ` ```hg1 ` block with base64url JSON `{v,intervalId,templateId,source,ado}`, optionally scrambled/AES-encrypted (per-install keychain key). Hidden on display, decoded for reconciliation, regenerated on write. Reconciliation-only — SQLite remains source of truth.

## ADR log

- **ADR-034 — Unoptimized dependencies made desktop crypto 66× slower; "Save" wasn't hanging, it took 93.7 seconds.** Saving a PAT reported `Stronghold save did not respond within 10000ms`. The app data dir held three 7-byte `hourglass.vault.hold.<hex>` files and **no** `hourglass.vault.hold`. Those 7 bytes decode as `50 41 52 54 49 03 00` = stronghold's `PARTI` magic + version 3, i.e. `write_to_snapshot` wrote its header and stalled inside the following `encrypt_content` — and, never reaching `rename`, left the temp file behind. **Measured, not inferred.** A standalone probe replicating `commit_with_keyprovider`: **93.7s** per snapshot write in a normal debug build. Adding `[profile.dev.package."*"] opt-level = 3`: **1.4s**. Same algorithms, same output bytes — purely codegen. The vault work is compress + age/ChaCha20-Poly1305 through `iota-crypto`/`libsodium`, and unoptimized Rust crypto runs 20–100× slower; every Settings "Save" writes the whole snapshot, so it blew past any sane timeout. **Fix:** `[profile.dev.package."*"] opt-level = 3` in `src-tauri/Cargo.toml` — optimize all dependencies, leave our own crate unoptimized and debuggable. This supersedes the narrower `rust-argon2`/`blake2b_simd` overrides added earlier (Argon2 also improves, ~870ms → ~50ms). One-time cost: a full dependency rebuild (~10 min); incremental builds are unaffected. **Two wrong turns worth recording.** (1) The very first round-trip probe *did* succeed and I read it as "persistence works, fast" — I never timed it, and mistook ~90s of execution for compile time. **Print timings in probes; an untimed pass can hide the bug you are hunting.** (2) When a later probe hung on a spawned thread but had passed on the main thread, that looked like a threading/`Send` deadlock — a tidy, plausible, wrong story. The A/B (main 93.7s vs spawned "hung" at a 45s cap) showed both were merely slow and my cutoff differed. **A timeout that differs between two runs will manufacture a false distinction.** **Consequence for the earlier ADRs:** ADR-032's corrupt snapshot was itself a *symptom* of this — each 90s+ save looked hung, got force-killed mid-write, and left a truncated file that then made `load_snapshot` spin. Fixing the slowness removes the mechanism that produced the corruption in the first place.
- **ADR-033 — `tauri-plugin-sql` cannot do transactions across IPC calls; desktop writes are non-atomic by necessity.** With SQLite (ADR-031) and the secret vault (ADR-032) both working, desktop startup then failed on `SqlError: cannot commit - no transaction is active`, thrown from `seedDemo` → `SqlWorkItemSectionRepository.upsert` → `TauriSqlDatabase.rawTransaction`. **Root cause, confirmed in the plugin source:** `DbPool::connect` builds an sqlx `Pool` with default options (10 connections) and `execute` runs `sqlx::query(&sql)` — a *prepared* query — via `pool.execute(...)`, acquiring a connection per call. Since `TauriSqlDatabase` issued `BEGIN`, the body statements, and `COMMIT` as **separate `invoke` calls**, they were served by *different pooled connections*: the `BEGIN` opened a transaction on one connection and the `COMMIT` arrived on another with nothing to commit. The plugin exposes no transaction command, no way to pin a connection, and no pool sizing; multi-statement SQL is impossible through a prepared query; and `DbPool`'s inner pool accessor is commented out, so a custom Rust command can't reach it either. **There is therefore no way to be atomic across this boundary short of forking the plugin.** **Decision:** `rawTransaction` now runs the work directly with no `BEGIN`/`COMMIT`/`ROLLBACK`, keeping the `SqlError` wrapping. `WasmSqlDatabase` (web) keeps real transactions; only the desktop path changes. **Accepted cost:** a multi-statement write — notably the delete-then-reinsert of a rule's/section's conditions — can be left half-applied if the app dies mid-write. This matches the localStorage backend, which has never been atomic. The sharpest edge is a mapping rule that loses its conditions and thus matches *everything*; worth revisiting if it ever bites, via upstream transaction support or a forked plugin command taking a statement batch. **The two `tauri-sql-database` transaction tests were inverted** (they previously asserted `BEGIN`/`COMMIT`/`ROLLBACK` were emitted — i.e. they locked in the broken behaviour and still passed, because the fake driver happily accepted statements a pooled sqlx never would) and now assert those keywords are absent, with a comment pointing here so nobody "restores" them. A third test covers the header/clear/re-insert ordering. **Lesson:** a fake that is more permissive than the real driver will happily certify a broken design — this bug was fully covered by green tests for two ADRs before a real database ever saw it.
- **ADR-032 (addendum) — the underlying hang was a corrupt Stronghold snapshot, and `load_snapshot` spins forever on one.** With the timeouts below in place, the silent stall became `TimeoutError: Stronghold vault load`, and per-step instrumentation narrowed it to `plugin:stronghold|initialize` (while `appDataDir`/`join` returned in single-digit ms, proving IPC itself was healthy). **Reproduced outside the app** with a standalone Rust binary mirroring the plugin's `Stronghold::new`: opening the existing `hourglass.vault.hold` **hung indefinitely (no result at 45s)**, while a fresh path returned in **81ms**. So `iota_stronghold`'s `load_snapshot` does not error on a truncated snapshot — it spins. **Origin:** three sibling `hourglass.vault.hold.<hex>` files of 7 bytes each, i.e. snapshot writes interrupted by force-killing the app during the earlier hangs — a self-reinforcing loop where each kill made the next start worse. **Resolution:** the four files were quarantined (moved, not deleted) and the probe then reported a clean fresh vault at the real path in 77ms; `hourglass.db` untouched. **Guard:** a `TimeoutError` from the initialize step is now rethrown naming the vault path and the remedy. Deliberately **not** auto-quarantined — a timeout cannot distinguish "corrupt snapshot" from "slow machine", and silently destroying a *valid* secrets file is a worse failure than a loud, actionable error. **Method note worth keeping:** two hypotheses were killed by measurement rather than argument — the earlier "stale frontend bundle" theory (settled by comparing generated `capabilities.json` mtime and console line numbers against source) and "unoptimized debug Argon2 is too slow" (benchmarked at 869ms against a 10s budget). Reproducing the suspect layer in a standalone binary was what finally converted speculation into proof; reach for that earlier next time a desktop adapter misbehaves.
- **ADR-032 — No timeouts anywhere on the desktop I/O path: "Saving…" hung forever with an empty console (timeout + healing-memo fix).** After ADR-031 unblocked SQLite, Settings→Save (both Harvest and ADO) sat on "Saving…" indefinitely with **zero console errors**. **Root cause — a class of bug, not one line.** Every desktop adapter bottoms out in a Tauri `invoke()`, which is a promise resolved *only* from an IPC callback; if the Rust side never replies, it stays pending forever. Critically, **a Rust panic produces exactly this**: the panic goes to the terminal, not devtools, and `tauri-plugin-stronghold`'s commands all do `collection.0.lock().unwrap()` on a `std::sync::Mutex`, so one panic poisons that mutex and *every* later stronghold call panics and hangs too. A trace of the save path (`saveHarvest`/`saveAdo` → repos → secrets → `reconfigure` → `probeHarvest` → `learnHarvestGuids` → `probeAdo`) found **not one** `setTimeout`, `AbortSignal`, `Promise.race`, or `connectTimeout` on it, and TanStack Query has no mutation timeout — so `isPending` could never clear. **Three memoized promises made it unrecoverable:** `RepositoriesFacade.backend`, `TauriSqlDatabase.ready`, and `StrongholdSecretStore.ready` each used the `if (!this.ready) this.ready = init()` idiom, which caches a *pending* promise as readily as a resolved one — one stalled vault load meant every subsequent `get`/`set` (and every retry click) awaited the same dead promise until an app restart. **Fixes.** New `infrastructure/async/with-timeout.ts`: `withTimeout(work, label, ms)` converts a stall into a diagnosable `TimeoutError` whose message names the step and points at "check the terminal running `tauri dev` for a Rust panic" (it bounds how long a *caller* waits — an in-flight IPC call can't actually be cancelled); `healingMemo(init, label, ms)` replaces the plain memo idiom and **discards a failed or timed-out attempt so the next call retries**. Applied at: `StrongholdSecretStore` (healing memo for the vault load + a bounded `step()` wrapper around every `insert`/`get`/`remove`/`save`, which also removed four copy-pasted try/catch blocks), `TauriSqlDatabase` (healing memo for init at 6× the budget since it also runs migrations, plus bounds on `execute`/`query`/driver load), and `TauriHttpTransport` (a whole-round-trip timeout, the previously-declared-but-never-set `connectTimeout` now actually passed to the plugin, and — a real second bug — `res.text()` moved *inside* the try/catch: it streams the body over repeated `fetch_read_body` IPC calls, so it could both stall and throw an unwrapped error). `ConnectionManager.reconfigure` now bounds `learnHarvestGuids` separately at 8s: it's explicitly best-effort, but it was `await`ed unconditionally on the critical path of every Save while doing a 90-day Harvest fetch. It stays awaited rather than fire-and-forget because four ADR-021 tests assert the learned GUID immediately after `reconfigure` — making it async would make them racy for no user-visible gain. **Two desktop-specific bugs found in the same trace and fixed:** (1) `stronghold-secret-store-factory.ts` built its vault path as `` `${dir}/${VAULT_FILE}` ``, but Windows `appDataDir()` returns backslashes — a mixed-separator path whose failed snapshot write inside the plugin's mutex-guarded command is exactly what poisons that mutex; now uses `join()` from `@tauri-apps/api/path`. (2) `src-tauri/src/lib.rs`'s Stronghold password closure ended in `.expect("failed to hash stronghold password")` — a panic *inside the `initialize` IPC command*, i.e. invisible and mutex-poisoning. Restructured so the closure never panics (logs to stderr and returns, letting the vault surface a decryption error instead of hanging), with the Argon2 config validated **once at startup** in `run()` where a failure is loud, immediate, and in the terminal. **Verified:** `cargo check` — compiles clean (1m08s). `npm run typecheck` — 0 errors. `npm run test` — **333 passing, 43 files** (+10 in `with-timeout.test.ts`, including the two regressions that matter: a never-settling promise now rejects with a `TimeoutError`, and a healing memo recovers on the call *after* a stall — the case that previously required an app restart). **NOT verified:** the actual desktop Save — no way to drive the Tauri window from here, and the user's live PATs were deliberately not used (a bad token produces an *error*, not a hang, so it would not have diagnosed this anyway). **Lesson:** treat every `invoke()` as an unbounded call from an untrusted process. Two rules for this codebase: (a) any await that crosses the IPC boundary needs a timeout, because the failure mode is a silent hang rather than an error; (b) never memoize a promise without clearing it on failure — a plain memo turns a transient stall into a permanent, restart-only outage.
- **ADR-031 — Desktop SQLite was silently denied by the capability layer: `sql:default` excludes `allow-execute` (fix + regression guard).** First real `npm run tauri dev` run logged `[persistence] Desktop SQLite unavailable — falling back to localStorage SqlError: tauri-sql execute failed`, with the stack pointing at `TauriSqlDatabase.init` line 52 — i.e. the **first** statement, `PRAGMA foreign_keys = ON`, before any migration ran (so this was not the ADR-030 v4 migration). **Root cause:** `tauri-plugin-sql`'s generated `default` permission set grants only `allow-close`, `allow-load`, `allow-select` — **not `allow-execute`**. `capabilities/default.json` listed just `sql:default`, so `Database.load` succeeded and every subsequent write was denied at the Tauri capability layer. This is exactly the "permission identifiers used per each plugin's documented convention but never cross-checked against the generated permissions schema" open item ADR-028 flagged; the schema (`src-tauri/gen/schemas/acl-manifests.json`) now exists because the user's toolchain has run `cargo build`, and checking it against the plugin manifests confirmed the gap. **The failure mode was doubly bad:** the denial was *silent* — `createRepositories`'s desktop branch catches any failure and falls back to `createLocalRepositories()`, so the app started and appeared to work while writing to localStorage instead of the real SQLite file. **Fixes:** (1) `capabilities/default.json` gained `"sql:allow-execute"`. (2) The same audit found `stronghold:default` omits `allow-remove-store-record`, which `StrongholdSecretStore.delete` invokes — deleting a stored PAT/token would have been denied the same way; added `"stronghold:allow-remove-store-record"`. `http:default` was checked and is complete (`allow-fetch` + friends). (3) **The real reason was being thrown away:** `TauriSqlDatabase`'s four catch blocks used `e instanceof Error ? e.message : '<generic>'`, but Tauri's `invoke` rejects with a plain **string** (here `"sql.execute not allowed. Permissions associated with this command: sql:allow-execute"`) — so the one piece of information that explained the failure was replaced by `'tauri-sql execute failed'`. New `driverErrorMessage(cause, fallback)` in `sql-error.ts` handles `Error` / bare string / `{message}` / opaque-object (JSON-serialized) causes, and all four sites now use it; `SqlError.cause` still carries the original. (4) **Regression guard:** new `src/infrastructure/tauri-capabilities.test.ts` cross-checks `capabilities/default.json` against the generated ACL manifest — it asserts every command the desktop adapters actually invoke (9 across sql/stronghold/http, each annotated with the calling code) is granted either directly or via that plugin's default set, and that no listed identifier is one the ACL doesn't define. The cross-checks `runIf` the manifest exists, so a clean checkout without a Rust toolchain skips rather than fails. Verified the guard catches the original bug: removing `sql:allow-execute` fails the suite with `sql:allow-execute — needed by TauriSqlDatabase.rawExecute — PRAGMA, migrations, every write`. **Verified:** `npm run typecheck` — 0 errors; `npm run test` — **323 passing, 42 files** (+9: 6 `sql-error.test.ts`, 3 capability-guard). **NOT verified here:** the actual desktop run — the capability grant is a Rust-side ACL change that only takes effect on a rebuild, so **the user must re-run `npm run tauri dev`** and confirm the fallback warning is gone. **Lesson (generalizes ADR-014's "done = smoke-tested"):** a Tauri plugin's `<plugin>:default` permission set is *not* "everything the plugin can do" — it is a curated, often read-only subset. Every command an adapter invokes needs an explicit audit against `gen/schemas/acl-manifests.json`, and a best-effort fallback around a platform adapter must log the *real* driver error or it will hide exactly this class of bug.
- **ADR-030 — Work-item rail sections, hierarchy, and one-level Task→Story parent fetch (verified in-browser).** Replaces the flat, unsorted, unsearchable work-item rail with user-defined collapsible sections over a parent/child tree. **Filter model reuse — no second engine:** `TemplateMatcher.ruleMatches` was refactored to delegate to a newly-exported `conditionsMatch(conditions, context)` in `domain/templates/mapping.ts`, so `WorkItemSection` (new `domain/work-items/work-item-section.ts`) carries a plain `MappingCondition[]` and is evaluated with the exact same operator set (`equals`/`contains`/`startsWith`/`regex`/`in`/`underPath`, `negate`, AND semantics) the mapping rules use; `templates.tsx`'s condition-row editor was extracted out of `RuleEditor` into a shared `ConditionRows` component and reused verbatim by the new `SectionEditor`. **Section assignment is root-level and first-match-wins:** `partitionIntoSections(items, sections)` builds the forest first (`buildWorkItemTree`, new `domain/work-items/work-item-tree.ts`), then matches each **root** against enabled sections in `sortOrder` order — descendants follow their root regardless of their own fields, so a Task is never torn away from its Story. Anything unmatched lands in a trailing `section: null` bucket rendered as **"Other"**, so a ticket can never silently disappear. **Ordering, not fetching, expresses the structure we don't retrieve:** each section owns `sortBy` (`default`=ADO's `ChangedDate DESC` order, `id`, `title`, `workItemType`, `state`, `iterationPath`) + `sortDirection` + `nestUnderParent` + `groupByParent`, applied by `orderSectionNodes` as sort → cluster → optional flatten. The `groupByParent` clustering is the key idea: two roots sharing a `parentId` (i.e. whose parent was *not* returned by the query) are pulled adjacent at the position of the first of them, so "all the user stories under Feature X" reads as a contiguous 1-2-3 run **without ever fetching Feature X**. **Parent fetching is deliberately one level and Task-only (the user's explicit call):** `WorkItem` gained `parentId` (mapped from a newly-requested `System.Parent` field in `ado-client.ts`); `fanOutWorkItems` collects the `parentId`s of items whose `workItemType` is in `PARENT_FETCH_TYPES = ['task']` and that aren't already present, issues **one** `ado.getWorkItems(connectionId, ids)` call per connection, and **stops** — a fetched Story never triggers a Feature lookup, a Feature never fetches its Epic. Gated on the new `Settings.fetchParentWorkItems` (default on, NULL-tolerant so pre-v4 rows read as `true`), best-effort (a failed lookup costs nesting, not tickets), and the whole fan-out now dedupes by `connectionId:id`. New port method `IAzureDevOpsClient.getWorkItems`; `runWiql`'s batch fetch was extracted into a `fetchByIds` that chunks at ADO's 200-id ceiling. **Search** is client-side and pure (`presentation/lib/work-item-search.ts`, modelled on `filterCommands`): `#123`/`123`/title/type/state/project/tags substring matching, and `filterWorkItemTree` **keeps the ancestors of a match** so a matched Task still reads under its Story; a live query force-expands everything. **Collapse state** lives in a localStorage-backed zustand store (`state/work-item-collapse.ts`, keys namespaced `sec:`/`wi:`), seeded once from `section.defaultCollapsed` after which the user's own toggling wins. **Persistence:** migration **v4** adds `work_item_section` + `work_item_section_condition` (mirroring the `mapping_rule`/`mapping_condition` pattern, including the transactional delete-and-reinsert upsert and `ON DELETE CASCADE`) and `settings.fetch_parent_work_items`; `SqlWorkItemSectionRepository` + a localStorage twin (`hourglass.workItemSections`) satisfy the new `IWorkItemSectionRepository` on both backends. Demo data was reshaped to exercise all of it (a Feature with two Stories, Tasks under one of them, and two Stories whose Feature #4700 is deliberately never fetched) plus three seeded demo sections. **Verified in the running app** (demo mode, `npm run dev`): sections render with counts; the Feature→Story→Task tree nests and each level collapses independently; collapse survives a page reload; searching "error states" returns the matching Task *with* its Story and Feature retained and drops the empty sections; flipping a section to `sortBy: id`/`desc` reorders the rail as expected; no console errors. **Not covered:** live ADO — the `System.Parent` field mapping and the real `getWorkItems` batch call are typecheck- and unit-tested (against fakes) only, never exercised against a real Azure DevOps instance; section conditions are still AND-only (no OR groups), inherited from the mapping engine; the "── parent #1234 ──" cluster divider sketched during planning was not built (clusters are contiguous but unlabelled).
- **ADR-029 — Multiple ADO tickets per time entry, with per-ticket hours allocation (verified in-browser).** A tracked entry could previously link to exactly one work item (`TimeInterval.workItemRef`), settable only at creation — the edit modal never exposed it. Real sessions cover several tickets. **Model:** new `WorkItemLink extends WorkItemRef` adds `title?` (cached so the UI needn't refetch), `hours?` (explicit attribution; `undefined` ⇒ share the remainder) and `syncedHours?` (what *this* ticket was last credited in ADO). `TimeInterval` gains `workItemLinks?: readonly WorkItemLink[]`; **`workItemRef` is retained as the primary** (always mirroring `workItemLinks[0]`) because Harvest's `external_reference` is singular and every pre-existing read path depends on it. `normalizeWorkItemLinks()` keeps the two in sync on every write and `workItemLinksOf()` reads either shape, so pre-v4 rows need no data migration. **Allocation** (`domain/services/work-item-allocation.ts`, pure): explicit hours are honoured verbatim; `remainder = max(0, total − Σ explicit)` is split evenly across the blank ones with the **last auto link absorbing the rounding drift** so allocations sum back to the entry's real hours; all-explicit sets are left alone and `allocationWarning()` surfaces over-claiming or unattributed time inline in the editor rather than silently rewriting the user's numbers. **Sync:** `pushToHarvest` still sends the **primary's** `buildAdoExternalReference` as the single Harvest `external_reference`, but the ADO write-back became a loop — `delta_i = allocated_i − (link.syncedHours ?? 0)` per ticket, each failure warned individually and that link's old figure retained so the delta is retried on the next push. Adding a second ticket to a 2h entry therefore debits the first by 1h and credits the new one 1h, rather than double-counting. When no live ADO client exists, `syncedHours` is deliberately **not** advanced, so hours accrued offline aren't skipped by the first real sync. `deleteInterval` reverses per link (falling back to the interval total for single-ticket pre-v4 rows). **`linkToHarvestEntry` re-baselines the links too** — this was caught by an existing ADR-022 regression test: adopting Harvest's hours into the interval-level `syncedHours` without re-spreading them across the links left the per-ticket baselines stale and the next edit's delta short. Harvest wins for the ADO baseline as well, not just the interval total. **Input plumbing:** `StartInput`/`ManualInput`/`UpdateIntervalInput` gained `workItemLinks`; because `definedOnly()` keeps defined values and an empty array *is* defined, `workItemLinks: []` clears every ticket with no sentinel — `updateInterval` additionally drops the stale `workItemRef` whenever a list is supplied, otherwise normalization would resurrect the primary from an empty list. **Persistence:** migration v4 adds `time_interval.work_item_refs` (JSON array, primary first) while the legacy `work_item_ref` column keeps holding the primary; `SqlTimeIntervalRepository.upsert`'s hand-written column list went 17→18. **UI:** the entry modal (both new and edit) gained an "Azure tickets" section — one row per link showing `#id · title`, a `primary` badge on the first with "make primary" on the others, an hours input whose *placeholder* shows the live auto-allocation, and a remove `×`; `+ Add Azure ticket` opens the new `work-item-picker-modal.tsx` (overlay + autofocused search + Arrow/Enter/Escape keyboard nav lifted from `command-palette.tsx`, multi-select with checkmarks, already-linked rows disabled). - **ADR-022 — Reconcile divergent hours on link (refines ADR-008/009; F10, agent-tested).** `TrackingService.linkToHarvestEntry` previously attached a local interval to an existing Harvest entry (`harvestTimeEntryId`) and already set `syncedHours` to the caller-supplied `entryHours`, but never compared that to the interval's own computed duration or surfaced a mismatch — explicitly deferred at ADR-009. Policy (**Harvest wins**, unchanged in spirit, now made explicit and observable): (1) `harvestTimeEntryId` is set as before; (2) Harvest's `hours` are adopted as `syncedHours` so the *next* edit's ADO CompletedWork delta (`newHours - syncedHours`) is computed against Harvest's real total, not the interval's own pre-link duration — this is what prevents double-counting on a later edit (proven by a new test: stop a WorkItem interval at 2h, link it to a Harvest entry whose real hours are 1.5, then extend it to 3h — the ADO delta pushed is `3 - 1.5 = 1.5`, not `3 - 2 = 1`); (3) **no Harvest write happens during link** (Harvest already has the entry) and **no ADO delta is emitted** (linking isn't new logged time) — this matches `importHarvestEntry`'s existing behavior for consistency; (4) local `start`/`end` are left completely untouched — analytics timing is preserved, only `syncedHours` reflects Harvest's truth. **Return-shape decision:** `linkToHarvestEntry` now returns `LinkToHarvestResult { interval: TimeInterval; reconciled: HoursReconciliation }` instead of a bare `TimeInterval` — `HoursReconciliation { localHours, harvestHours, adopted, diverged }` (`adopted` always equals `harvestHours`, kept as a separate field for clarity at call sites and to leave room for a future "use local instead" mode without another shape change). `diverged` is `Math.abs(localHours - harvestHours) > 0.01` and only computed when the interval isn't still running (`current.end !== undefined`) — a running interval's "duration so far" isn't a meaningful thing to diverge against. - **ADR-019 — Aggregate same-task-per-day roll-up (refines ADR-006 & ADR-008; F8a, agent-tested).** Behind the already-wired, OFF-by-default `Settings.aggregateSameTaskPerDay` flag, multiple same-day intervals sharing a `(harvestProjectId, harvestTaskId)` pair can now share **one** Harvest entry instead of each getting its own. Core invariant: a Harvest entry's `hours` = Σ `syncedHours` over every local interval carrying its `harvestTimeEntryId` — for a solo entry that's just the interval's own `syncedHours`, identical to today. The generalization is implemented as a **pure domain helper**, `domain/services/rollup.ts`: `resolveRollup({ interval, dayIntervals, aggregate })` returns `{ entryId?, siblingHours }` — (1) if the interval is already linked, roll into that same entry and sum every *other* same-day interval sharing that id (excludes self by id, so re-stopping a continued/edited interval never double-counts itself); (2) else, only when `aggregate` is on, look among the day's intervals for ones sharing the same project+task **and** an existing `harvestTimeEntryId`, group them by that id, and adopt the group whose earliest-started member started first (deterministic pick when a task somehow has more than one existing entry that day); (3) otherwise (aggregate off, or nothing to join) → `{ entryId: undefined, siblingHours: 0 }`, i.e. no roll-up — a fresh entry will be created holding just this interval's own hours. `sumSyncedHours` (also exported, `undefined → 0`) is the shared summation primitive, reused by both the resolver and `TrackingService.deleteInterval`'s patch-down path. **`TrackingService.pushToHarvest`** now destructures `aggregateSameTaskPerDay` off `settings.get()`, fetches the day's intervals (`listByDate(interval.date)` — called *before* the current interval's own upsert, so it never includes the not-yet-persisted current interval; `resolveRollup` excludes self by id regardless, as a second guard), calls `resolveRollup`, and computes `absoluteHours = round2(siblingHours + hours)`: if `entryId` resolved, `harvest.updateTimeEntry(entryId, { hours: absoluteHours, ... })` (patches the shared entry to the new group total); else `createTimeEntry({ hours: absoluteHours, ... })` (== `hours` when solo, so OFF/solo is byte-for-byte the pre-existing behavior). The **ADO CompletedWork delta block is untouched** — `delta = round2(hours - (interval.syncedHours ?? 0))`, still computed per-interval, never against the group sum — and the returned interval still carries `syncedHours: hours` (this interval's own contribution only, not the group total), so per-member ADO bookkeeping and the timesheet's per-interval hours stay exactly as before; only the value pushed to the *shared Harvest entry* changes. **`TrackingService.deleteInterval`** changes from unconditional `deleteTimeEntry` to **patch-down-else-delete**: fetch the interval (`get(id)`) *before* deleting it locally, then delete; if it had a `harvestTimeEntryId` and a Harvest client is configured, compute `remaining` = the day's intervals still sharing that id (naturally excludes the just-deleted one, since local delete already happened) — if `remaining.length === 0`, `deleteTimeEntry` (solo/OFF case: deletes exactly as before); otherwise `updateTimeEntry(id, { hours: round2(sumSyncedHours(remaining)) })` (patches the shared entry down to the survivors' total). Both new remote calls are wrapped in the existing try/catch-warn pattern — never throws, never blocks the local delete. **Forward-only**: no retro-consolidation pass merges pre-existing separate entries when the flag is turned on after the fact; roll-up only ever joins entries going forward from intervals still resolvable via `listByDate`. **Tests**: `domain/services/rollup.test.ts` (8 cases, pure) covers solo/OFF-unlinked (no rollup), OFF-but-self-linked (sums other same-entry sharers, excludes a different entry), ON-first-of-task (nothing to join), ON-one-linked-sibling (joins it), ON-re-stop-excludes-self, ON-multiple-candidate-entries (earliest-start wins), ON-different-task-or-date (no rollup), and `sumSyncedHours` undefined-safety. `application/tracking-service.test.ts` gained a new `describe('aggregateSameTaskPerDay roll-up')` block (6 cases) proving: ON two-stops-same-task/day → one create + one patch to the cumulative sum, correct per-interval ADO deltas, a third stop keeps patching the cumulative total; OFF (default settings, unchanged) → two creates, explicit `harvest.updated` length-0 assertion (no cross-update); ON `continueInterval` on a group member then stopping → patches the sum, no new create; ON `updateInterval` on a member → patches the recomputed sum, ADO gets only that member's own delta; ON delete-one-of-two → patches the entry down to the survivor (not deleted) with the correct ADO decrement, then deleting the survivor actually deletes the Harvest entry (`harvest.deleted` asserted) with its own ADO decrement; - **ADR-006 — Each Start = separate Harvest entry.** Per user requirement (no roll-up). Optional aggregate toggle deferred to Phase 2. *(Update, F8a: the deferred toggle is now implemented — see ADR-019. Default behavior is unchanged; roll-up only activates when `Settings.aggregateSameTaskPerDay` is explicitly turned on.)*
- **ADR-010 — Enforce the Harvest-link invariant, end to end.** `TrackingService.startTracking`/`logManualTime`/`updateInterval` now throw `UnmappedEntryError` (`domain/errors.ts`) when the resolved project+task is missing/partial — refusing to persist an entry Harvest can't represent. At the UI boundary, `EntryModal` no longer auto-defaults a new entry's project to the first option (a silent guess defeats the point); the Save/Start/Add button is disabled with a hint until a project **and** task are chosen. Start/Log actions whose mapping rule doesn't resolve (`WorkItemCard`, `MeetingCard`, quick templates) no longer call `startTracking` directly — they route through a global `useEntryModalStore` (`presentation/state/entry-modal.ts`) that opens the same modal prefilled with the original context (notes, `workItemRef`, `templateId`, `source`, and a meeting's computed duration for "Log"), so the user picks a mapping without losing why the entry was started. Already-mapped items keep the zero-friction one-click Start. Continuing/importing/linking don't need the guard (they never introduce a fresh unmapped entry).
- **ADR-009 — Harvest is the source of truth (refines ADR-002).** Per product direction, a persisted entry is meaningful only when linked to a Harvest entry (`harvestTimeEntryId`); local SQLite is the working cache/link + analytics store, not the authority. Consequences implemented: (a) **hg1 stores only non-native data** — `{ v, source, templateId? }`; project/task/notes/hours/date and the ADO link (native `external_reference`) are dropped. Embedding is **opt-in via `Settings.embedMetadata` (default false)** and, even when on, only written when non-default; turning it off strips the tag on the next sync (keeps Harvest notes clean by default). (b) **Never push `hours ≤ 0`** — Harvest treats a timeless entry as a *running* timer, which would collide with our local timing (dual timer); we time locally and always push explicit positive hours on stop. (c) **Harvest entries are first-class**: `importHarvestEntry` adopts an external entry into a local interval; `linkToHarvestEntry` attaches a local interval to an existing Harvest entry; external (Harvest-only) rows support Start (new timer)/Edit(adopt+update)/Delete(`deleteTimeEntry`). (d) **Delete moved into the edit modal** behind a two-step confirm (card delete was too easy to hit). Deferred: blocking starts that can't map to Harvest. *(Update, F10: reconciling divergent hours on link is now implemented — see ADR-022.)*
- **ADR-008 — Edit/restart/manual entries + Harvest-entry reconciliation.** `TimeInterval` gained `syncedHours` (hours last pushed) so edits push **absolute** hours to Harvest but only the **delta** (`newHours − syncedHours`) to ADO CompletedWork — no double-counting on re-sync. `TrackingService.updateInterval` (marks `isManual`, re-derives hours from start/end, re-pushes) and `continueInterval` (reopens the SAME stopped interval — shifts `start` back by the already-logged time so the clock resumes from the accrued total and the next stop updates the same Harvest entry; **not** a clone — the user wants to continue, not restart) added. The timesheet reconciles by `harvestTimeEntryId`: Harvest entries matching a local interval are hidden (local wins, editable); unmatched Harvest entries render **read-only** ("Harvest" badge) and count toward day/week totals. Editing/adopting those external entries is deferred. Manual/edit uses one modal (`entry-modal.tsx`) with an optional time editor — any of start+end, start+duration, end+duration, or duration-only (fields kept in sync; times are local HH:MM ↔ ISO). New + all-blank → live `startTracking`; otherwise `logManualTime`/`updateInterval` with the resolved start/end. Web dev pulls entries through the Vite proxy (ADR-003/007).
- **ADR-007 — Runtime connection wiring via a `ConnectionManager` + lazy client providers.** Real Harvest/ADO adapters are built from persisted config + secrets by `infrastructure/connections/connection-manager.ts`, which holds the live clients and rebuilds them on `reconfigure()` (called after any Settings save). It lives in infrastructure because it constructs concrete adapters; the composition root wires it and the container falls back to seeded demo data whenever `configured()` is false. `TrackingService.harvest/ado` became **provider functions** (`() => IHarvestClient | undefined`) so the manager can swap the underlying client without rebuilding the service and so demo mode skips sync silently (no spurious warnings). Rejected: rebuilding the whole container/tracking-service on config change (the container is a stable singleton read live by hooks) and always-present delegating clients (would emit false sync warnings in demo mode). Secrets go through `ISecretStore`; the web/dev adapter (`LocalSecretStore`) is localStorage-backed (**not** hardware-backed) and is swapped for the OS keychain (Tauri stronghold) on desktop behind the same port. `IHttpTransport` currently resolves to `FetchHttpTransport` for both platforms (`createHttpTransport()`); the Tauri native branch (no CORS) slots in there later. ADR-003's CORS caveat stands: live Harvest/ADO calls only work in the desktop shell (or via a web proxy) — the plain web build will fail direct calls.
